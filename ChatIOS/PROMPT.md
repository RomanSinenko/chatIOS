# Что важно про backend
Backend уже существует и умеет базовый chat MVP.

Основные готовые HTTP endpoints:
- `POST /auth/dev-login` — временный вход/регистрация по телефону без SMS, телефон в JSON body
- `POST /users/{username}?display_name=...` — старый dev endpoint создания пользователя с custom username. В текущем iOS-flow не использовать для входа/регистрации
- `GET /users/search?query=...` — поиск пользователей только по `username`, требует `Authorization`
- `POST /private-chats` — найти или создать private chat, требует `Authorization`, собеседник в body
- `GET /users/me/chats` — список чатов текущего пользователя, требует `Authorization`
- `GET /chats/{chat_id}` — мета-информация о чате, требует `Authorization`
- `GET /chats/{chat_id}/messages?limit=50&offset=0` — история сообщений с membership check, требует `Authorization`

WebSocket:
- `WS /ws` — подключение с `Authorization: Bearer <session_token>`

Формат исходящего сообщения от клиента:

```json
{
  "type": "send_message",
  "client_message_id": "client-generated-id",
  "chat_id": 1,
  "to_user_id": 2,
  "text": "hello"
}
```

Форматы входящих событий с сервера:
- `message`
- `system`
- `error`
- `message_ack`

Что уже поддерживается на backend:
- временный dev-login по телефону без SMS
- `username` как публичный уникальный идентификатор
- `display_name` как неуникальное отображаемое имя, может быть `null`
- отдельная таблица телефонов пользователя
- единая backend-логика отображения собеседника:
  - сейчас `display_name`, если есть, иначе `username`
  - телефон другим пользователям не показывается
- private chat flow
- self-chat
- список чатов
- история сообщений
- WebSocket realtime через `WS /ws`; текущая задача iOS — подключить клиентскую отправку/приём событий
- `message_ack`
- membership checks

# Что сделано в шаге `ios-fix-authenticated-chat-list`
Ветка: `ios-fix-authenticated-chat-list`

Причина шага:
- backend перешёл на защищённые endpoints через `session_token`
- старый iOS-контракт с `user_id` в URL/query перестал подходить

Сделано:
- `ContentView` хранит `sessionToken`, полученный из `DevLoginResponse`
- `ChatsListView`, `NewMessageView`, `ChatView` получают `sessionToken`
- `APIClient.devLogin(phone:)` отправляет телефон в JSON body
- `APIClient.getUserChats(sessionToken:)` вызывает `GET /users/me/chats`
- `APIClient.fetchMessages(chatID:sessionToken:)` вызывает `GET /chats/{chat_id}/messages?limit=50&offset=0`
- `APIClient.searchUsers(query:sessionToken:)` вызывает `GET /users/search?query=...`
- `APIClient.getOrCreatePrivateChat(peerUserID:sessionToken:)` вызывает `POST /private-chats`
- все защищённые HTTP-запросы отправляют `Authorization: Bearer <session_token>`
- `user_id` больше не отправляется в URL/query для авторизации
- `user_id` остаётся локально в iOS только для UI-логики:
  - определить, какие сообщения мои
  - убрать текущего пользователя из результатов поиска

Важно:
- если пользователь ищет свой же `username`, backend/frontend могут вернуть пустой результат намеренно
- текущего пользователя нельзя выбирать как собеседника через global search

# Формат нашей работы
Работаем так:
- сначала определяем крупный шаг, который нужно сделать
- под этот шаг создаём отдельную git-ветку
- дальше двигаемся короткими шагами
- на каждом коротком шаге AI пишет:
  - в какой файл нужно внести код
  - какую функцию, структуру или часть кода нужно добавить
  - сам код для вставки
- после кода AI отдельно объясняет:
  - как это работает
  - зачем это нужно
  - какие новые методы, функции или конструкции там использованы
- пользователь переписывает код вручную сам
- после того как пользователь переписал код и всё прочитал, он присылает `"+"`
- сообщение `"+"` означает: можно двигаться дальше к следующему короткому шагу

Важно:
- AI не должен торопиться и перескакивать через шаги
- AI не должен выдавать сразу большой объём реализации на много шагов вперёд
- один ответ = один понятный короткий шаг в рамках текущего большого шага

# Завершение большого шага
Когда большой шаг завершён:
- обновляем `PROMPT.md` по аналогии с backend-подходом
- фиксируем, что именно было сделано в рамках шага
- сразу определяем следующий большой шаг
- после этого делаем `git push`
- затем продолжаем работу уже от следующего большого шага

Это нужно, чтобы:
- сохранять живой контекст проекта
- не терять прогресс между этапами
- всегда понимать текущее состояние iOS-части
